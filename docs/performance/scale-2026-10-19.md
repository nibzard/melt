# Workspace size and concurrent requests, 2026-10-19

These measurements precede the [workspace scale fixes](scale-fixes-2026-10-19.md).

This run measures larger v0.1 workspaces through the framed service entry point.
It finds a restart failure, a table cache capacity problem, and contention on the workspace lock.
No runtime behavior or service limits change in this measurement.

The workspace fixtures contain 8 projections and 16 parameters, or 32 projections and 256 parameters.
The larger fixture reaches the default projection and parameter limits.
All projections reference one shared table. Actions and bindings are absent; edits do not run Python code.
Each history fixture starts in a separate workspace and commits 20, 100, or 500 parameter edits.
The last 20 edits provide the commit latency samples.

Reopen includes service startup, workspace inspection, and service shutdown.
Successful reopen measurements use five samples. A failure stops that fixture after its first failed reopen.
The 32-projection workspace fails to reopen after just 20 successful edits.
The storage scan tries to return 1,838,544 bytes through a 1,048,576-byte frame.
The scan uses a record count limit of 200; it does not size pages by encoded bytes.
At 100 and 500 edits, the failing scan response exceeds five million bytes.
The benchmark records these errors and preserves the workspaces. It does not raise the frame limit.
The data remains on disk; the standard service open path fails.

Table workloads use 32 projections, 256 parameters, and 20 columns.
Each caller requests 20 pages of 50 rows with no pause between requests.
A barrier starts 1, 4, or 8 caller threads together. Each thread waits for its response before sending another request.
This is a closed-loop workload, not a fixed arrival-rate load test.

The one-million-row table fits the 256 MiB cache. The three-million-row table does not.
The latter retains no decoded table between unsorted page requests, so every page decodes the complete table.
The operating system cache stays warm; these are not cold disk measurements.
Extra callers add queueing rather than increasing read throughput.

For mixed workloads, one caller edits parameter p0 while the other callers read pages.
Only one caller writes, so revision conflicts do not affect these timings.
The sort workload changes a numeric filter on every request and sorts score descending.
The filter keeps nearly all rows; this is a full-sort stress workload.
That prevents reuse of the sorted row order, while allowing reuse of the decoded table when it fits.

The benchmark wraps the existing reentrant workspace lock and measures outermost acquisition wait and ownership time.
Nested acquisitions do not count twice. It changes no lock ordering or critical sections.
Threads call process_frame directly on one owning service. There is no network or separate client process.
The stdio serve loop is serial; this benchmark measures contention inside the service, not parallel stdio handling.
These results cover one workspace at a time and do not measure independent workspaces running together.
Each table size runs in a fresh Python process. Fixture creation and import are outside the timed request samples.
Raw records include resident memory after each workload. This includes fixture allocation retention and excludes the Node helper.
It is not peak process memory and is not equivalent to retained cache bytes.
Each workload is one exploratory run. The p95 uses nearest rank; small sample counts limit tail estimates.
All measured page and edit responses succeed. Commit sequence checks verify the expected number of writes.
Restart failures are recorded separately. Durability facts remain WAL mode with synchronous=2.

The next work should follow this order:

1. Bound storage scan responses by encoded bytes and test reopening after many large snapshots.
2. Read only the Parquet batches needed for an unsorted page and cache bounded batches.
3. Resolve immutable read inputs under the workspace lock, then perform decoding and sorting outside it.
4. Avoid full compilation for parameter-only changes, while preserving revision and state checks.
5. Reduce repeated history scans or add checkpoints after the scan framing failure is fixed.

These measurements identify work that remains useful without a language rewrite.

Run the benchmark with:

```sh
uv run --locked python3 scripts/benchmark_scale.py \
  --output build/benchmarks/scale.json
```

Use `--rows 2000 --requests 2 --history 0 4` for a small smoke run.
The script creates a fresh temporary data directory unless you supply a new `--root` path.
It prints the directory and keeps the workspaces for inspection.
The JSON records environment facts, workload sizes, raw request samples, memory readings, and exact restart errors.
